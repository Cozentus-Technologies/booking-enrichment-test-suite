8.2Release impact rules

  • BlockingSeverity S1, or raised against a scenario tagged critical. The release does not proceed until the defect is fixed and the scenario re-executed successfully.
  • ConditionalSeverity S2 against a high-priority scenario. The release proceeds only with a named owner, an agreed fix date and product owner sign-off recorded against this report.
  • Non-blockingSeverity S3 or below against a medium or low priority scenario. Logged and scheduled; does not affect the release decision.
  • DeferredAccepted into a later cycle with written product owner agreement. Carried forward on the next report as known debt.

10.1Coverage summary

Coverage here is scenario coverage against spec/test-cases.yaml: the catalogued test cases this cycle executed, as a share of the cases the catalogue defines. It is not, and does not approximate, code coverage.

Code coverage is out of scope for this report. This is a black-box suite: it reaches the service only through Kafka and its readiness endpoint, and has no visibility of a line or a branch inside it. Instruction and branch coverage are owned by the development team's own unit tests and reported separately. No figure anywhere in this report is derived from the service's source.
